# H8/3003 control firmware: analysis notes (v2.0, `korgpro20` ic22)

Addresses and behaviour only. Listings, traces and anything containing firmware bytes stay under
`data/analysis/` (gitignored). Tools: `reference/wsl/trace_h8.sh` (PC trace + replay trace in one
run), `tools/h8trace_analyze.py`, `tools/h8_dsp_writers.py`, `reference/h8dasm` (recursive-descent
disassembler seeded with executed PCs, on MAME's H8 disassembler: dev only).

The translator's input comes from `tools/h8dec.py`: our H8/300H decoder with reference/h8dasm's
traversal (vectors, `--entry`, `--entries` seeds; runs stop at rts / rte / jmp / sleep; the
unconditional `bt` runs on). Its IR equals h8dasm's line for line on the v2.0 ic22: the translation
input (the seed list `romdata/korgpro20_h8_seeds.txt` expanded, 10,432 lines, giving the same
`h8_gen.cpp`), the vectors alone (2,250) and every even address as a seed (210,961 lines, data
regions included).

### Address lists (`romdata/<set>_h8_seeds.txt`, `_h8_entries.txt`)

| Line | Meaning |
|---|---|
| `0112e6` | one code address (hex) |
| `table 00e7ca 26 4` | 26 big-endian 32-bit pointers, 4 bytes apart, read from your ic22 at 0x00E7CA (CPU byte order) |

The ROM's pointer arrays and {key, pointer} dispatch records are ascending, so a plain sorted list
of their targets reproduces stretches of them (before 2026-11-19: up to 26 pointers in a row; the
audit then missed bare-hex lists). `tools/h8_addrlist.py pack` moves every stretch of two or more
consecutive addresses that lies in the ROM at one stride (up to 32 bytes) into a table line;
`check` confirms none is left (also contiguous 24/32-bit, either endianness, either byte order of
the dump); `expand` (run by the build) gives back the plain list.

| Item | Value | Evidence |
|---|---|---|
| Clock | 12.288 MHz (24.576 MHz / 2), 256 H8 cycles per 48 kHz frame | driver `h8_clock` |
| Mode | MD2:0 = 2: 1 MiB advanced mode, 16-bit bus; I/O registers at 0xFFFxx; 32-bit vector table | driver `set_mode_a20(true)` |

| DMAC channel 0 | 0xFFF20-0xFFF2F (MAR/ETCR/DTCR A and B) drives buffer to DSP port transfers | send routine |

## Native boot (no emulator snapshot)

`Synth::load` on a data folder without `state.bin` / `ram.bin` powers the firmware on itself
(`Synth::boot_native`, `H8Control::boot`); `engine/tools/native_boot` writes the resulting
snapshot, and the DSP compiler, the Windows app and the plugin save it after a native boot.

| Step | What runs | Evidence |
|---|---|---|
| Reset | the translated reset handler (vector 0, 0x010594): I/O and RTOS set-up, the init routines (0x010708), the boot program loads (DSP3 effects, DSP2 filter, DSP1 oscillator set 0, then the clear program and the A00 sets); its switch into the first task returns to the native scheduler | DMA log: the oracle's load order |
| V55 power-on stream | 1.4747 s after reset: `80 00 90 00 a0 00 c0 01`, User Scale 1 and 2 at their defaults (12 + 128 `b0` entries); 368 frames later the controller resets, 46 frames later A00's program record; 8,342 frames later, one message every 82 frames: the panel controllers (A00's Controller Assignment bytes 0, 4, 1, 2, 3, 6, then aftertouch; wheel 2 at its centre), Porta SW, the Performance Editor edits | oracle UART capture (`control_korgpro20_p000`, 1,142 bytes before 10.9 s): equal byte for byte |
| Snapshot | frame 523,185 (10.9 s, on an H8 tick) | |

The firmware's fixed wait in the program-change routine (`mov.l #0x38000, er0` / `dec.l` / `bne`
at 0x0124BC, 6 states per iteration = 5,376 frames) lets the clear program just loaded into DSP1 and
DSP3 wipe their delay memory before the next programs arrive. The native layer counts its iterations
(`Cpu::delay_pc`) and holds the DSP host operations that follow it in the same event (program
loads, mute, coefficient writes, in order per DSP) until that time has passed. The oracle shows
5,454 / 5,581 frames (DSP1) and 6,573 / 6,753 (DSP3) from the clear load to the next one.

| Check | Result |
|---|---|
| Native snapshot vs the oracle's (10.9 s) | programs, ST0/ST1 equal on all three DSPs; H8 RAM: 219 of 131,072 SRAM bytes differ (RTOS/stack area), on-chip 83 of 512 (stack); load offset 456 frames (UART pacing) |
| Output from each snapshot (`synth_render`, 128 programs) | 122 of 128 programs bit-identical; programs 0-5 differ (DSP running state at the snapshot) |
| Coefficient memory 0.9 s after each bank-A program change vs the oracle | oracle snapshot: 47,690 / 49,152 words equal before the timed wait, 47,778 with it; native snapshot with it: 47,736 |
| Determinism | native snapshots from GCC (compiled and interpreter cores) and MSVC builds are byte-identical (the board allocates its cores zero-filled, as MAME does) |
| Suites on the native snapshot | program_test, pe_test, param_test, arp_test, dsp_fast_test (plain, --chaos, --budget), plugin_test: pass |

## RTOS task model (for the translated control layer)

Task descriptors: ROM 0x0000F4 + 10*n = {u32 entry, u32 initial SP, u16 priority} (0 = highest).
Kernel: start task 0x0109C6 (r0 = n), exit/yield 0x010BEC, wait 0x010D38, mailbox init 0x010D9E,
post 0x010CD8 (r0 = n), ISR exit 0x010FDA.

| Task | Entry | Prio | Shape | Role |
|---|---|---|---|---|
| 0 | 0x01ACDC | 0 | loop: wait, dequeue (0x01AB02), dispatch via table 0x01AC9C by type | V55 message handler |
| 1 | 0x01AD0A | 0 | exits immediately | idle |
| 2 | 0x012528 | 3 | run-to-exit: 27 dirty-flag bytes at RAM 0x048700, handlers via table 0x00E7AA | parameter recompute |
| 3 | 0x019A16 | 2 | run-to-exit: 6 x 0x0189C6, 4 x 0x019692, 0x019AF0, 0x01B106 | per-tick modulation |
| 4 | 0x01138C | 1 | loop: wait, drain 4-byte queue (RAM 0x040984/0x040988), dispatch via 0x011370 | internal events |

Tick: WOVI ISR 0x0106AE starts task 3 every 49,920 H8 cycles = 195 DSP frames (246.15 Hz).
Engine scheduling: run-to-completion with priority preemption at start/post; unwind on exit/wait.
